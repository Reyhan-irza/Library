You are working on the VIREON Library System.

## PHASE 3 — ADMIN OPERATIONS, INVENTORY CONTROL, RETURNS & LIBRARY MANAGEMENT

Your task is to implement and polish the operational library-management layer of VIREON.

This phase focuses ONLY on authenticated admin operations and library inventory workflows.

Do not redesign unrelated public landing pages.
Do not rebuild the authentication system.
Do not replace the existing architecture.
Do not introduce fake/mock data where real Supabase data already exists.

The system must remain production-oriented, consistent, secure, responsive, and maintainable.

==================================================
5. INVENTORY MANAGEMENT
==================================================

Inventory integrity is critical.

The system must maintain:

total_stock
available_stock
borrowed_stock

Where appropriate, borrowed_stock may be derived instead of stored.

Do not maintain duplicated values unless necessary.

Core invariant:

available_stock must never be negative.

When a borrowing is approved:

available stock must be revalidated server-side/database-side.

When a book is returned:

available stock must be restored exactly once.

Prevent:

- Double approval
- Double return
- Over-allocation
- Negative inventory
- Duplicate transaction effects
- Race conditions

Do not rely solely on frontend checks.

Critical inventory operations must be protected at the database/backend layer.

Reuse existing request/transaction structures whenever possible.

21. CONCURRENCY & DATA INTEGRITY
==================================================

This is a critical requirement.

Consider this scenario:

Book has 1 available copy.

Student A requests it.
Student B requests it almost simultaneously.

The system must NOT allow both transactions to consume the same final copy.

Availability must be validated atomically where necessary.

The frontend check is not sufficient.

Use appropriate Supabase/PostgreSQL mechanisms such as:

- transactional database functions
- conditional updates
- row-level locking where appropriate
- atomic inventory updates

Choose the approach compatible with the existing schema.

Do not introduce an unnecessarily complex architecture.
